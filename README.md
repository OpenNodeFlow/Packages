# OpenNodeFlow Packages

Public Git source for optional OpenNodeFlow packages. The application image ships no pack catalog. It starts with an empty library; an administrator reviews, trusts and explicitly installs packages from this repository or another configured Git repository.

The current **2.2.0 foundations release** contains 37 package families with repository-defined artwork and presentation metadata. Recommended defaults are **Core, Runtime, Shared types, Utilities and Logic**. Runtime includes named work queues with 15 typed operations; Logic gathers general decisions and adds twelve reusable nodes. Provider-specific types no longer appear in default package dependency closures. See [FOUNDATIONS.md](FOUNDATIONS.md) for queue usage, organization migration, custom package branding and validation. Older release details below remain historical provenance; the repository retains all 107 release manifests.

`onf-packages.json` is the root catalog. `packages/core/2.0.0.json` contains ten reviewed static core definitions: manual/webhook/schedule entries, object/text/number/boolean constants, custom TypeScript pass-through, condition and delay. `packages/runtime/2.0.0.json` contains 224 static typed storage, variables, joins, durable waits, error-reporting and remote-route definitions. They retain their original exact definition IDs and versions, including variable v1 compatibility. Package release 2.0.0 and an individual definition's integer version are separate identities. No production database, credentials, workflow history or publication journal was exported. `PROVENANCE.json` and `PROVENANCE-RUNTIME.json` record source fingerprints.

The retained 2.0.0/2.1.0 catalog contains **36 package families**. The 2.0.0 baseline has 1,938 archived definition revisions. The 2.1.0 structural release adds 34 manifests, updates 846 existing asset identities and adds 2,565 definitions: 853 structural types and 1,712 codec nodes. Optional families include Azure and Azure DevOps REST, Kubernetes/operators, Prometheus/Loki/Grafana/Alertmanager, containers/networking, GitHub/GitLab/Gitea, Jira/Confluence, Slack/Discord/Notion, Sentry/PagerDuty, Microsoft Teams, HubSpot, Xero, Google Analytics/Ads and WebSockets. Utilities include typed HTTP/GraphQL, text, dates, collections, files/SQLite, XML/mail and reusable compositions. Each family manifest embeds its exact transitive dependency closure, so it can be installed independently; duplicate dependency versions remain byte-identical across packages.

These generic definitions preserve the canonical IDs/pins of the historical 21–22 October audited source factories. The 2.1.0 release incorporates the reviewed 23 October public structural overlay for collaboration, cloud/infrastructure and Azure DevOps. `STRUCTURAL-MIGRATION.md` records its scope and deliberate exclusions; `PROVENANCE-STRUCTURAL.json` records original and adapted source fingerprints. Private PR automation controllers, office endpoints and model contexts are absent. Provider availability, permissions and current API behavior still require independent verification before live use.

Install through ONF's Packages page:

1. Select the official source, or add your public `https://github.com/OWNER/REPOSITORY` source. A configurable branch/tag/ref is resolved to a full immutable commit when refreshed.
2. Refresh the catalog. Preview the selected release and inspect its source, definition bodies, declared effects and affected workflows. Commit, digest and archived dependency details remain available for provenance. A preview is review data; follow the per-node documentation for provider scopes, connection names and effects.
3. Explicitly trust the source and accept executable code for the chosen installation. Review and separately confirm any reported breaking changes; a stale impact preview requires another preview. Installed packages are executable server code, with the permissions of the worker; source trust is a security decision.
4. Add the resulting Core/Runtime packs to the desired workspace through Library → Packs. Installation does not run nodes, activate triggers, register webhooks or repin existing graphs. Runtime storage/variable operations deliberately mutate ONF state when subsequently executed; review their exact documentation.

The official public repository is [OpenNodeFlow/Packages](https://github.com/OpenNodeFlow/Packages). An operator can override the default before first boot with `ONF_OFFICIAL_PACKAGES_REPOSITORY` and `ONF_OFFICIAL_PACKAGES_REF`. Catalog refresh, source trust and installation remain separate deliberate actions.

Other HTTPS Git hosts require the administrator to add the exact hostname to `ONF_PACKAGE_GIT_HOSTS` (comma-separated) and install Git in the ONF container. Example: `ONF_PACKAGE_GIT_HOSTS=git.example.com,gitlab.com`. Then add a public `https://git.example.com/team/onf-packs.git` source. GitHub uses bounded HTTP API/raw-file requests. Other approved hosts use isolated bare shallow fetches without a checkout, hooks, credentials, submodules or install scripts. Private authenticated repositories and SSH transport are not supported in this release.

Author a package by copying the manifest structure, choosing a unique stable package ID and definition IDs, documenting ports/configuration/setup/effects/failure/retry behavior, and creating exact custom-type/executor/subflow pins. Node bodies are async function bodies using `inputs`, `config`, `context`; they are not Node modules. Do not add package install scripts or dependencies. Types, nodes, triggers, executors, codecs and subflows follow the application's existing definition/import contracts. Packages may declare required secret names; runtime secret values must never enter a repository.

The manifest has `schemaVersion:1`, `id`, `name`, semantic `version`, `description`, `permissions`, `definitions`, and optional `libraryPacks`, `libraryFolders`, `libraryMetadata`. It cannot contain workflow instances, workspace selections, secret values, storage, history, ingress credentials or files to extract. `permissions` declares secret names, `network`, `filesystem` and explanatory text; it is review information, not a runtime sandbox policy. Include every new exact dependency in the package, or ensure the referenced immutable version is already installed. Existing organization metadata must remain byte-identical unless an explicit reviewed libraryMigrations block matches its exact prior rows and same-source provenance. Ordinary user organization changes still use their guarded API; package updates never overwrite customized rows.

Publishing is an explicit Git commit/push:

1. Add a new `packages/FAMILY/VERSION.json` file. Never replace the bytes of a released manifest or previously published definition ID/version. Add next immutable definition versions for changed behavior.
2. Compute the file's SHA256 and add `{id,name,version,description,path,sha256}` to the root catalog. Preserve older release entries and immutable dependency versions.
3. Run `npm run check` and `npm test`; also validate against the actual ONF package preview/import API in an isolated instance and test code with injected/mock transports. The local check verifies catalog/digests/documentation and pure Core/Runtime boundaries; it is not the app's full schema/runtime test. `npm run build:integrations -- --check` reproduces the generic manifests in memory from this repository's allowlisted pure `src/builders` sources and stripped stable identity map, without writes, sibling repositories or network calls. The baseline builder remains `2.0.0`. Use `npm run build:structural -- --check` for the reviewed structural `2.1.0` release; do not use the baseline builder to occupy that release identity. After review, omit `--check` to append its new manifests/catalog entries locally. This never pushes or installs them. All historical catalog entries, release bytes and definition ID/version contents are checked before any output is written; changed behavior requires a new definition version as well as a new package release. Identical regeneration is a no-op. The builder preserves unrelated and older releases, uses exclusive creation for new manifests and replaces the catalog only after the new files exist. A failed filesystem write can leave unreferenced new manifests; an identical rerun accepts those bytes. Catalog/summary replacements use unique temporary files owned by that attempt and clean them up on failure. The derived, non-authoritative summary is written under the catalog lock and repaired even when a retry adds no releases. Symlink/junction components are rejected before reads and writes. Conflicting files or a retained build lock require investigation. Core/Runtime manifests remain separately authored.
4. Review the diff for credentials, unbounded I/O and unintended effects. Push a reviewed commit and optionally tag it. Installing/updating remains a separate administrator decision in each ONF instance.

The loader records source URL, full commit, package version, exact SHA256, definition pins and installation revision. Refreshes never install or update code automatically. Updating a package retains archived definitions and changes the current definition of each existing logical asset. Live workflows follow the current asset identity; saved run/history snapshots retain their historical bytes. Ordinary editing uses Save changes or Save as new identity. The integer definition revision and package release are internal history/provenance details, not separate assets to choose during authoring. There is no install-time external action, auto-enable, install hook, dependency execution or archive extraction. Removing workspace discovery does not delete historical definitions. Uninstall/garbage collection, signed publisher identity and private repository authentication remain future work. The original 36 baseline manifests passed the actual ONF validator and atomic package installer against fresh isolated SQLite data with mocked Git HTTP; `VALIDATION.json` records exact digests, 1,938 installed immutable versions, zero workflows and zero node-body executions. That proof did not contact real providers.

The structural builder and tests are standalone: `npm ci`, `npm test`, `npm run build:structural -- --check`. Tests compile every changed/new schema and node body, exercise all structural codec pairs with synthetic optional/null/extension values, and exercise 307 cloud operations, 15 Azure DevOps operations and the Jira/Slack response corrections using injected mock transports. They never contact providers. All 70 baseline and structural release manifests passed the actual v2 package preview and atomic installer with mocked Git in fresh temporary SQLite: 5,349 retained definition revisions, 4,501 current logical assets, zero workflows and no node execution. Current-asset diagnostics found zero catalog errors. `VALIDATION-STRUCTURAL.json` records the exact artifact digests. New manifests remain local release artifacts until an explicitly reviewed commit is published.

To repeat the actual app import check, run `scripts/validate-app.mjs --app <v2-checkout>` with Node and that v2 checkout's `tsx` import loader. The script rejects a non-v2 app package, creates and removes its own temporary SQLite directory, serves only local artifacts through a mock Git transport, installs the retained baseline before the structural releases, and writes the public evidence summary. It neither starts an app server nor executes installed nodes.
