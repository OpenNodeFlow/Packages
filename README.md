# OpenNodeFlow Packages

Public Git source for optional OpenNodeFlow packages. The application image ships no pack catalog. It starts with an empty library; an administrator reviews, trusts and explicitly installs packages from this repository or another configured Git repository.

`onf-packages.json` is the root catalog. `packages/core/2.0.0.json` contains ten reviewed static core definitions: manual/webhook/schedule entries, object/text/number/boolean constants, custom TypeScript pass-through, condition and delay. `packages/runtime/2.0.0.json` contains 224 static typed storage, variables, joins, durable waits, error-reporting and remote-route definitions. They retain their original exact definition IDs and versions, including variable v1 compatibility. Package release 2.0.0 and an individual definition's integer version are separate identities. No production database, credentials, workflow history or publication journal was exported. `PROVENANCE.json` and `PROVENANCE-RUNTIME.json` record source fingerprints.

The catalog contains **36 packages and 1,938 distinct immutable definition versions** in total, including 1,704 generic integration/type definitions. Optional families include Azure and Azure DevOps REST, Kubernetes/operators, Prometheus/Loki/Grafana/Alertmanager, containers/networking, GitHub/GitLab/Gitea, Jira/Confluence, Slack/Discord/Notion, Sentry/PagerDuty, Microsoft Teams, HubSpot, Xero, Google Analytics/Ads and WebSockets. Utilities include typed HTTP/GraphQL, text, dates, collections, files/SQLite, XML/mail and reusable compositions. Each family manifest embeds its exact transitive dependency closure, so it can be installed independently; duplicate dependency versions remain byte-identical across packages.

These generic definitions preserve the canonical IDs/pins of the historical 21–22 October audited source factories. The later 23 October structural-overlay migration and office-specific Azure ingress/model policies are deliberately excluded from this public migration. Private PR automation controllers and office endpoints are absent. Provider availability, permissions and current API behavior require independent verification before live use; the baseline does not claim every later v1 catalog refinement is already represented.

Install through ONF's Packages page:

1. Select the official source, or add your public `https://github.com/OWNER/REPOSITORY` source. A configurable branch/tag/ref is resolved to a full immutable commit when refreshed.
2. Refresh the catalog. Preview a selected version and inspect its commit, digest, definition bodies, dependency pins and declared effects. A preview is review data; follow the per-node documentation for provider scopes, connection names and effects.
3. Explicitly trust the source and accept executable code for the chosen installation. Installed packages are executable server code, with the permissions of the worker; source trust is a security decision.
4. Add the resulting Core/Runtime packs to the desired workspace through Library → Packs. Installation does not run nodes, activate triggers, register webhooks or repin existing graphs. Runtime storage/variable operations deliberately mutate ONF state when subsequently executed; review their exact documentation.

The official public repository is [OpenNodeFlow/Packages](https://github.com/OpenNodeFlow/Packages), published on27October2026. The application loader resolved the initial GitHub commit and verified all36manifest SHA256 digests over real HTTPS. An operator can override the default before first boot with `ONF_OFFICIAL_PACKAGES_REPOSITORY` and `ONF_OFFICIAL_PACKAGES_REF`. Catalog refresh, source trust and installation remain separate deliberate actions.

Other HTTPS Git hosts require the administrator to add the exact hostname to `ONF_PACKAGE_GIT_HOSTS` (comma-separated) and install Git in the ONF container. Example: `ONF_PACKAGE_GIT_HOSTS=git.example.com,gitlab.com`. Then add a public `https://git.example.com/team/onf-packs.git` source. GitHub uses bounded HTTP API/raw-file requests. Other approved hosts use isolated bare shallow fetches without a checkout, hooks, credentials, submodules or install scripts. Private authenticated repositories and SSH transport are not supported in this release.

Author a package by copying the manifest structure, choosing a unique stable package ID and definition IDs, documenting ports/configuration/setup/effects/failure/retry behavior, and creating exact custom-type/executor/subflow pins. Node bodies are async function bodies using `inputs`, `config`, `context`; they are not Node modules. Do not add package install scripts or dependencies. Types, nodes, triggers, executors, codecs and subflows follow the application's existing definition/import contracts. Packages may declare required secret names; runtime secret values must never enter a repository.

The manifest has `schemaVersion:1`, `id`, `name`, semantic `version`, `description`, `permissions`, `definitions`, and optional `libraryPacks`, `libraryFolders`, `libraryMetadata`. It cannot contain workflow instances, workspace selections, secret values, storage, history, ingress credentials or files to extract. `permissions` declares secret names, `network`, `filesystem` and explanatory text; it is review information, not a runtime sandbox policy. Include every new exact dependency in the package, or ensure the referenced immutable version is already installed. Organization metadata must remain byte-identical when it already exists; changing shared organization uses its ordinary guarded API.

Publishing is an explicit Git commit/push:

1. Add a new `packages/FAMILY/VERSION.json` file. Never replace the bytes of a released manifest or previously published definition ID/version. Add next immutable definition versions for changed behavior.
2. Compute the file's SHA256 and add `{id,name,version,description,path,sha256}` to the root catalog. Preserve older release entries and immutable dependency versions.
3. Run `npm run check`; also validate against the actual ONF package preview/import API in an isolated instance and test code with injected/mock transports. The local check verifies catalog/digests/documentation and pure Core/Runtime boundaries; it is not the app's full schema/runtime test. `npm run build:integrations` reproduces the generic manifests from this repository's allowlisted pure `src/builders` sources and stripped stable identity map, without sibling repositories or network calls.
4. Review the diff for credentials, unbounded I/O and unintended effects. Push a reviewed commit and optionally tag it. Installing/updating remains a separate administrator decision in each ONF instance.

The loader records source URL, full commit, package version, exact SHA256, definition pins and installation revision. Refreshes never install or update code automatically. Updating a package adds immutable definitions while retaining old versions; workflows keep their pins until deliberately upgraded. There is no install-time external action, auto-enable, install hook, dependency execution or archive extraction. Removing workspace discovery does not delete historical definitions. Uninstall/garbage collection, signed publisher identity, private repository authentication and the latest structural-overlay migration remain future work. All 36 manifests passed the actual ONF validator and atomic package installer against fresh isolated SQLite data with mocked Git HTTP; `VALIDATION.json` records exact digests, 1,938 installed immutable versions, zero workflows and zero node-body executions. That proof did not contact real providers.
